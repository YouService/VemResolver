## 1.1 Visão Geral do Sistema

VemResolver é um monólito modular com separação clara em dois processos
independentes:

* Processo backend: Spring Boot (JAR executável), responsável por toda a lógica
  de negócio, persistência e segurança, expondo uma API REST/JSON
* Processo frontend: Angular Single Page Application, responsável pela interface
  do usuário, servida como arquivos estáticos (Node 22-alpine no container)
* Banco de dados: PostgreSQL 16-alpine, acessado exclusivamente pelo backend via
  Spring Data JPA/Hibernate

A comunicação entre frontend e backend ocorre exclusivamente via HTTP/REST com
payloads JSON. Não há GraphQL, WebSocket ou chamadas diretas ao banco pelo
frontend.

## 1.5 Segurança

### Cadeia de Filtros (SecurityFilterChain — SecurityConfig)

* CSRF: desabilitado (API stateless)
* Sessão: SessionCreationPolicy.STATELESS
* Regras de autorização por path+método:
  - /api/auth/** — permitAll
  - GET /api/categorias/** — permitAll
  - POST, PUT, DELETE /api/categorias/** — hasRole("ADMIN")
  - /swagger-ui/**, /api-docs/**, /swagger-ui.html — permitAll
  - GET /api/prestadores/** — permitAll
  - POST /api/prestadores/** — hasRole("PRESTADOR")
  - qualquer outra requisição — authenticated()
* Headers de segurança: frameOptions().deny() (anti-clickjacking);
  xssProtection desabilitado em favor de padrões modernos

### Fluxo de Autenticação

1. Cliente envia POST /api/auth/login com LoginDTO (email, senha)
2. AuthService.login() chama authenticationManager.authenticate() com
   UsernamePasswordAuthenticationToken(email, senha)
3. DaoAuthenticationProvider delega para CustomUserDetailsService.
   loadUserByUsername(email) que executa userRepository.findByEmail(email)
4. Se as credenciais são válidas e user.isEnabled() (ativo == true): autenticado
5. JwtTokenProvider.generateToken() gera o JWT assinado com HMAC-SHA (chave
   derivada de ${JWT_SECRET} decodificado em Base64)
6. RefreshTokenService.generateRefreshToken() cria o registro em refresh_tokens
7. Resposta: AuthResponseDTO com token (JWT 24h) e refreshToken (7 dias)

### Fluxo de Validacao de Token em Cada Requisição

1. JwtAuthenticationFilter.doFilterInternal() extrai o header Authorization
2. Se presente e começar com "Bearer ": extrai o token (substring(7)) e chama
   jwtTokenProvider.extractUsername(token)
3. Se username extraído e SecurityContext vazio: carrega UserDetails via
   CustomUserDetailsService e valida o token com jwtTokenProvider.validateToken
4. Se válido: popula o SecurityContext com UsernamePasswordAuthenticationToken
5. filterChain.doFilter() segue o processamento normal

### Renovação (Refresh)

1. Cliente envia POST /api/auth/refresh com RefreshRequestDTO
2. RefreshTokenService.validateAndRotate() busca o token, verifica revoked e
   expiryDate
3. refreshTokenRepository.deleteByUser(user) exclui o token atual
4. Novo RefreshToken é criado e persistido
5. JwtTokenProvider.generateToken() gera novo JWT
6. Retorno: AuthResponseDTO com novo token e novo refreshToken

### CORS

* Configurado em SecurityConfig.corsConfigurationSource()
* Origins via frontendUrl (@Value("${app.frontend.url}"))
* Métodos: GET, POST, PUT, PATCH, DELETE, OPTIONS
* Headers permitidos: Authorization, Content-Type
* Header exposto: Authorization
* allowCredentials: true

# 3. FLUXO DE SEQUÊNCIA TEXTUAL — Contratação de Prestador (Aceitar Proposta)
================================================================================

Este fluxo descreve em detalhe o que acontece internamente quando um cliente
autenticado aceita uma proposta via PATCH /api/propostas/{id}/aceitar.

1. O cliente envia a requisição:
   PATCH /api/propostas/42/aceitar
   Authorization: Bearer <jwt_token>

2. A requisição chega ao JwtAuthenticationFilter.doFilterInternal():
   * O header Authorization é lido e o prefixo "Bearer " removido
   * JwtTokenProvider.extractUsername(token) extrai o subject (email do usuário)
     do payload JWT via JJWT
   * Como o SecurityContext está vazio, CustomUserDetailsService.
     loadUserByUsername(email) busca o usuário no banco via
     userRepository.findByEmail(email)
   * JwtTokenProvider.validateToken(token, userDetails) verifica assinatura e
     expiração
   * UsernamePasswordAuthenticationToken é criado e populado no SecurityContext
   * filterChain.doFilter() passa o controle adiante

3. O SecurityFilterChain verifica a autorização:
   * O path /api/propostas/{id}/aceitar não corresponde a nenhuma regra
     específica, caindo em anyRequest().authenticated()
   * Como o SecurityContext foi populado no passo 2, a requisição é autorizada

4. PropostaController.aceitar() é invocado:
   * @AuthenticationPrincipal User user é resolvido a partir do SecurityContext
   * O método delega: propostaService.aceitarProposta(42L, user.getId())

5. PropostaService.aceitarProposta(42L, clienteId) executa dentro de uma
   transação @Transactional:

   a. Busca a proposta:
      proposta = propostaRepository.findById(42L)
      Se não existir: lança ResourceNotFoundException("Proposta não encontrada")

   b. Verifica posse:
      proposta.getSolicitacao().getCliente().getId() deve ser igual a clienteId
      Se diferente: lança BusinessException("Apenas o cliente dono da
      solicitação pode aceitar propostas")

   c. Verifica status:
      proposta.getStatus() deve ser StatusProposta.ENVIADA
      Se diferente: lança BusinessException("Esta proposta já foi processada")

   d. Atualiza o status da proposta:
      proposta.setStatus(StatusProposta.ACEITA)

   e. Atualiza o status da solicitação (via referência lazy já carregada):
      proposta.getSolicitacao().setStatus(StatusSolicitacao.EM_ANDAMENTO)

   f. Persiste a proposta:
      proposta = propostaRepository.save(proposta)

   g. Persiste a solicitação separadamente:
      solicitacaoRepository.save(proposta.getSolicitacao())

   h. Converte para DTO e retorna:
      return toDTO(proposta) — PropostaDTO com todos os campos preenchidos,
      incluindo a flag foiAvaliadoPeloPrestador calculada via
      avaliacaoRepository.existsBySolicitacaoIdAndTipo

6. PropostaController retorna:
   ResponseEntity<PropostaDTO> com HTTP 200 e o PropostaDTO no corpo

7. O cliente recebe a resposta:
   * PropostaDTO com status = ACEITA
   * A solicitação associada passa a aparecer como EM_ANDAMENTO nos dashboards
     (GET /api/solicitacoes/minhas e GET /api/solicitacoes/abertas já não a
     incluem nos resultados ABERTA)
   * As demais propostas da mesma solicitação permanecem com status ENVIADA —
     o cliente pode recusá-las individualmente via PATCH /api/propostas/{id}/recusar
